## Структура
- `data/raw/` — сырой CSV (не в git). Ссылка и SHA256 в `data/raw/README.md`.
- `data/splits/` — train/val/test индексы (в git). Не пересобирать без согласования.

- `scripts/<имя>/` — личные скрипты.
- `outputs/<имя>/` — модели, графики (не в git).

## Правила работы
- В `main` напрямую не пушим. Только через PR из своей ветки.
- Перед созданием ветки: `git checkout main && git pull`.
- Ветка называется `<имя>/кратко-задача`, например `vlad/uplift-baseline`.
- Работаем только в своих папках `notebooks/<имя>/` и `scripts/<имя>/`.






# 📘 Регламент работы с репозиторием (через GitHub Desktop)

Этот документ описывает правила совместной работы. Мы используем схему **Fork** (опционально) или **Collaborator** (прямая работа) с обязательным созданием **Pull Request (PR)**. 

> ⚠️ **ВАЖНО:** Ветка `main` защищена. Никто (включая авторов) не может пушить изменения напрямую в `main` или сливать PR без одобрения мейнтейнера (владельца репозитория).

---

## 👨‍💻 ЧАСТЬ 1: Инструкция для коллег (Авторов изменений)

### 1. Первоначальная настройка (делается один раз)
1. Откройте **GitHub Desktop**.
2. Нажмите `File` -> `Clone repository`.
3. Выберите ваш репозиторий из списка (или вставьте ссылку на него) и нажмите `Clone`.
4. Выберите локальную папку на компьютере, где будет храниться проект.

### 2. Ежедневный рабочий процесс (Перед началом работы)
1. Откройте **GitHub Desktop**.
2. Убедитесь, что в верхнем меню **Current Branch** выбрана ветка `main`.
3. Нажмите кнопку **Fetch origin** (вверху справа). Если появятся изменения, кнопка сменится на **Pull origin** — нажмите её, чтобы скачать свежую версию `main`.
4. Нажмите **Current Branch** -> **New Branch**.
5. Назовите ветку понятным именем (например, `feature/add-login` или `fix/header-bug`) и нажмите **Create Branch**. Вы автоматически переключитесь на эту новую ветку.

### 3. Внесение изменений и коммит
1. Откройте проект в вашем редакторе кода (VS Code, PyCharm и т.д.) и внесите нужные правки.
2. Вернитесь в **GitHub Desktop**. Вы увидите список измененных файлов на вкладке `Changes`.
3. Внизу слева в поле **Summary** напишите краткое описание того, что вы сделали (например: "Добавил форму авторизации").
4. Нажмите кнопку **Commit to [имя вашей ветки]**.
5. Повторяйте шаги 3-4 по мере необходимости.

### 4. Отправка изменений и создание Pull Request (PR)
1. В **GitHub Desktop** нажмите кнопку **Publish branch** (если ветка новая) или **Push origin** (если вы уже пушили ранее).
2. После пуша в интерфейсе GitHub Desktop появится кнопка **Create Pull Request**. Нажмите на неё (откроется браузер).
3. На сайте GitHub убедитесь, что:
   * **base:** `main` (куда вливаем)
   * **compare:** ваша рабочая ветка (откуда вливаем)
4. Заполните заголовок (Title) и описание (Description). Опишите, что именно вы поменяли и зачем.
5. Нажмите зеленую кнопку **Create pull request**.
6. **Готово!** Теперь ждите, пока мейнтейнер (владелец) проверит ваш код и вльет его.

---

## 🛡️ ЧАСТЬ 2: Инструкция для мейнтейнера (Владельца)

Вы получаете уведомления, когда кто-то создает PR. Ваша задача — проверить код и принять решение.

### 1. Проверка кода (Code Review)
1. Зайдите на страницу репозитория на GitHub и перейдите во вкладку **Pull requests**.
2. Откройте новый PR.
3. Перейдите на вкладку **Files changed**, чтобы увидеть, какие именно строки кода были добавлены (зеленым) или удалены (красным).
4. Вы можете оставить комментарий к конкретной строке, нажав на плюсик рядом с номером строки.
5. Если нужно что-то исправить, напишите об этом в комментариях (коллега сделает коммит в свою ветку, и PR обновится автоматически).

### 2. Одобрение (Approval)
1. Если код хороший и ошибок нет, нажмите кнопку **Review changes** в правом верхнем углу.
2. Выберите пункт **Approve** (Одобрить).
3. (Опционально) Напишите комментарий, например: "Отличная работа!".
4. Нажмите **Submit review**.

### 3. Слияние (Merge)
1. После вашего одобрения (и если нет конфликтов) внизу страницы PR появится большая зеленая кнопка **Merge pull request**.
2. Нажмите её.
3. Нажмите **Confirm merge**.
4. (Рекомендуется) Нажмите кнопку **Delete branch**. Это удалит рабочую ветку коллеги с сервера, чтобы не засорять репозиторий. Сам PR при этом сохранится в истории.

## 💡 Полезные советы и решение проблем

### Что делать, если GitHub Desktop пишет о конфликтах (Conflicts)?
Если пока вы работали, кто-то другой уже влил свои изменения в `main`, и они пересекаются с вашими:
1. В GitHub Desktop переключитесь на `main` и нажмите **Pull origin**.
2. Переключитесь обратно на свою ветку.
3. Нажмите **Branch** -> **Update from main** (или найдите кнопку Merge/Rebase в интерфейсе). GitHub Desktop попросит открыть редактор для разрешения конфликтов.
4. Исправьте конфликты в редакторе, сохраните файлы.
5. Вернитесь в GitHub Desktop, закоммитьте изменения и сделайте **Push origin**.

### Как обновить PR, если мейнтейнер попросил внести правки?
1. Просто внесите правки в той же ветке на своем компьютере.
2. Сделайте коммит (Commit).
3. Нажмите **Push origin**.
4. PR на сайте GitHub обновится автоматически, повторно создавать его не нужно!

### Правило хорошего тона
* Всегда создавайте новую ветку под каждую новую задачу. Не смешивайте фиксы разных багов в одной ветке.
* Пишите понятные сообщения коммитов (Summary).

## Что коммитится, а что нет
- **В git:** код (`scripts/`), ноутбуки (`notebooks/`), `data/splits/*.npy`, `requirements.txt`, `README.md`, финальные отчёты (`reports/`).
- **Не в git:** `data/raw/`, `data/processed/`, `outputs/`, `.venv/`, все `*.pkl`, `*.parquet`, `*.zip`, `*.gz`, а также `*.png` и `*.csv` **вне** `reports/`.

Если сомневаетесь, должен ли файл быть в git, — спросите руководителя (или нейронку) перед `git add`.
